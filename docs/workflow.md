# workflow.md
> 위치: `docs/workflow.md`
> 이 문서는 팀 공통 자산이다. 새 프로젝트마다 새로 만들지 않고 팀 템플릿 repo에서 가져온다.

사람이 "결정"하고, AI가 "실행"한다.

---

## 시작 (하루 또는 세션 시작)

### 1. 컨텍스트 로드

**이 단계는 사용하는 AI 개발 도구에 따라 방식이 다르다. `docs/onboarding.md` 3번 참고.**

이 프로젝트 구조는 아래 파일들을 AI가 읽어야 제대로 작동한다.

```
.ai/config.md          ← AI 역할 / 작업 방식 / 기준 파일 정의
.ai/memory/context.md  ← 프로젝트 전체 맥락
.ai/memory/personal.md ← 개인 코딩 스타일 (없으면 personal.example.md를 복사해서 생성)
.ai/memory/patterns.md ← 패턴 / 안티패턴
```

이 파일들을 AI가 읽으면 매 세션마다 프로젝트를 "처음 만나는 사람"이 아니라
"이미 알고 있는 동료"처럼 동작한다.

---

### 2. 작업 정의

처음 시작할 때는 `tasks/current.example.md`를 `tasks/current.md`로 복사한다.
그다음 `tasks/current.md`를 열어 오늘 할 작업을 정의한다.
정의가 끝나면 AI 요청을 통해 실제 코드를 `src/` 안에 작성한다.

```
tasks/current.example.md → current.md 작성 예시 템플릿 (팀 공유)
tasks/current.md         ← 무엇을 만들지 정의 (개인 작업)
        ↓
   AI 실행 요청
        ↓
    src/ 코드      ← 실제 결과물 (AI + 사람 검증)
```

**활성 스킬 지정 (선택):**

이 작업에서 특정 스킬을 사용하고 싶으면 `## 활성 스킬` 섹션을 추가한다.

```
## 활성 스킬
- .ai/skills/ecommerce/SKILL.md
```

- git에 올라가지 않으므로 개인 설정으로 관리됨
- 템플릿은 `tasks/current.example.md`에 남겨두고 실제 작업만 `tasks/current.md`에 적는다
- 작업이 바뀔 때 스킬도 함께 교체하거나 제거하면 됨
- 스킬이 없으면 섹션 자체를 생략해도 됨

> config.md에 "활성 스킬이 명시된 경우 해당 스킬을 참조한다"가 설정되어 있어
> 별도 명령 없이 AI가 자동으로 읽는다.

```
# 현재 작업 (2024-06-01)

## 목표
회원가입 API 구현

## 요구사항
- 이메일, 비밀번호 입력
- 중복 이메일 체크
- 비밀번호 해싱

## 완료 기준
- [ ] 회원 생성 API 정상 동작
- [ ] 중복 이메일 시 에러 반환
- [ ] 비밀번호 해싱 적용 확인

## 진행 상태
- [x] 프로젝트 초기 세팅 (완료)
- [ ] 회원가입 API (진행 중) ← 지금 여기
- [ ] 로그인 API (다음)
```

**핵심 포인트**
- "어떻게 구현할지" 쓰지 않는다 → AI가 결정하게 둔다
- "무엇이 되어야 하는지"만 쓴다 → 결과 중심으로 작성
- 완료 기준은 체크리스트로 → 나중에 검증할 때 그대로 쓴다

잘못된 예시:
```
# ❌ 이렇게 쓰지 않는다
## 목표
UserController에 POST /auth/signup 엔드포인트 만들고
UserService에서 bcrypt로 해싱하고 prisma로 저장
```

올바른 예시:
```
# ✅ 이렇게 쓴다
## 목표
회원가입 기능 구현

## 요구사항
- 이메일 중복 체크
- 비밀번호 해싱 저장
- 성공/실패 응답 반환
```

## 반복 (작업 사이클)

### 3. AI 실행 요청

`tasks/current.md` 작성이 끝나면 작업 유형에 맞는 프롬프트 템플릿을 사용한다.

**사용 방법:**
1. `.ai/prompts/` 폴더에서 해당 템플릿 파일을 연다
2. 템플릿 내용을 참고해서 AI에게 요청한다
3. 기본 요청은 한 줄로 충분하다

| 작업 유형 | 템플릿 파일 | 기본 요청 한 줄 |
|---|---|---|
| 기능 개발 | `.ai/prompts/feature.md` | `tasks/current.md` 기준으로 기능 구현해줘 |
| 버그 수정 | `.ai/prompts/bugfix.md` | `tasks/current.md` 기준으로 버그 수정해줘 |
| 리팩토링 | `.ai/prompts/refactor.md` | `tasks/current.md` 기준으로 리팩토링해줘 |
| 코드 리뷰 | `.ai/prompts/review.md` | `tasks/current.md` 완료 항목 코드 리뷰해줘 |

config.md에 "tasks/current.md를 기준으로 한다", "rules.md, patterns.md를 준수한다"가
설정되어 있으므로 AI는 이미 그 내용을 알고 있다.
추가 맥락이 필요할 때만 템플릿의 나머지 항목을 채워서 보완한다.

> 파일 참조 방식은 도구마다 다르다. `docs/onboarding.md` 3번 참고.

**추가 맥락이 필요한 경우 예시:**
```
tasks/current.md 기준으로 기능 구현해줘.

추가로:
- 기존 UserService 패턴 그대로 따를 것
- src/services/user.service.ts 참고
```

### 4. 코드 검증 (사람)

AI가 생성한 코드를 받으면 아래 3가지만 확인한다.
전체를 다 이해하려고 하지 않아도 된다.

```
1. 요구사항 맞는가?      → current.md의 완료 기준 체크리스트와 대조
2. 구조 깨지 않았는가?   → map.md의 폴더 구조와 비교
3. 이상한 추상화 없는가? → 불필요하게 복잡하거나 과도하게 나뉘지 않았는가
```

수정이 필요하면 구체적으로 한 줄로 요청한다.

```
# 수정 요청 예시
컨트롤러 너무 두꺼움 → 서비스로 분리해줘
에러 처리 빠진 것 같음 → 중복 이메일 케이스 추가해줘
네이밍이 rules.md랑 다름 → camelCase로 통일해줘
```

한 번에 완벽한 코드를 기대하지 않는다.
요청 → 검증 → 수정 요청 → 재검증 사이클을 빠르게 반복하는 게 맞다.

> AI는 초안을 만든다. 판단은 사람이 한다.

### 5. 막혔을 때

AI가 엉뚱한 결과를 내거나 방향이 불명확할 때는 다음 순서로 점검한다.

**1단계 — context.md 확인**
```
.ai/memory/context.md를 열어서
- 프로젝트 목표와 현재 단계가 최신 상태인지 확인
- 오래된 정보가 있으면 먼저 업데이트
```

**2단계 — map.md 확인**
```
.ai/map.md를 열어서
- 지금 작업이 어느 레이어에 해당하는지 확인
- 기존 구조와 충돌하는 부분이 있는지 점검
```

**3단계 — 요청 재정의**
```
current.md의 목표와 요구사항을 더 명확하게 다시 쓴다.
요청이 모호할수록 AI도 모호하게 답한다.
```

**4단계 — 범위 축소**
```
한 번에 너무 많은 걸 요청하고 있는 건 아닌지 확인한다.
크면 작게 나눠서 하나씩 요청한다.
```

### 6. 패턴 축적

다음 상황에서 `.ai/memory/patterns.md`에 기록한다.

**기록해야 할 때:**
- 좋은 코드 구조가 나왔을 때
- 같은 문제가 2번 이상 반복됐을 때
- AI가 계속 같은 실수를 할 때

**작성 방법:**
```
## [패턴 이름]
- [규칙 또는 구조 설명]
- [왜 이렇게 하는지]

## 안티패턴
- [하면 안 되는 것] → [왜 안 되는지]
```

**실제 예시:**
```
## 회원가입 구조 패턴
- Controller → Service → Repository 3레이어 유지
- Validation은 Controller에서 처리
- 비즈니스 로직은 Service에서만 처리
- DB 접근은 Repository에서만

## 안티패턴
- Controller에 직접 DB 쿼리 금지 → 레이어 분리 원칙 위반
- Service에서 HTTP 응답 객체 사용 금지 → 재사용성 저하
```

> 규칙을 만들려고 억지로 쓰지 않는다.
> 실제로 문제가 생겼거나 반복되는 것만 기록한다.
> 이게 쌓일수록 AI가 더 정확해진다.

### 7. 의사결정 기록

기술 선택, 구조 변경, 중요한 판단이 생기면
`docs/decisions.md`에 즉시 기록한다.

**기록해야 할 상황:**
- 라이브러리를 선택했을 때
- 구조를 변경했을 때
- 여러 옵션 중 하나를 골랐을 때
- "왜 이렇게 했지?"라는 질문이 나올 수 있는 모든 것

**작성 방법:**
```
# [결정 제목] (날짜)

## 배경
## 선택지
## 결정
## 이유
## 트레이드오프
## 영향 범위
## 관련 작업 (task, PR 등)
```

**실제 예시:**
```
# Controller-Service 구조 채택 (2024-06-01)

## 배경
API가 늘어나면서 라우터에 비즈니스 로직이 섞이기 시작

## 선택지
- 라우터에 직접 작성 (현재 방식)
- Controller + Service 분리
- Clean Architecture 도입

## 결정
Controller + Service 분리

## 이유
라우터 직접 작성은 유지보수 어려움.
Clean Architecture는 현재 규모에 과도함.

## 트레이드오프
파일 수 증가, 초기 구조 잡는 시간 필요

## 영향 범위
src/controllers/, src/services/ 전체

## 관련 작업
tasks/current.md
```

> "나중에 기록하지" → 항상 까먹는다.
> 결정하는 순간 바로 쓴다.
> 이거 안 하면 3개월 뒤 내가 고통받는다.

### 8. 코딩 규칙을 바꿔야 할 때

1. `.ai/rules.md` 수정
2. `.airules` 반드시 동기화 (이 두 파일이 다르면 AI가 엉뚱하게 동작함)
3. 팀이면 PR + 리뷰 거침

### 9. src/ 구조가 바뀔 때

`src/`에 새 폴더나 레이어가 생기거나 구조가 변경되면
반드시 `.ai/map.md`를 업데이트한다.

**업데이트가 필요한 상황:**
- 새 폴더 추가 (예: `src/controllers/`, `src/repositories/`)
- 기존 폴더 역할 변경
- 레이어 구조 변경 (예: 2레이어 → 3레이어)

**업데이트하지 않으면:**
- AI가 없는 폴더에 코드를 생성하거나 잘못된 경로로 import
- 구조 원칙을 모르고 패턴 위반 코드 생성

> map.md는 AI의 지도다. 지도가 낡으면 AI가 길을 잃는다.

---

### 10. 작업이 너무 많아질 때 (컨텍스트 압축)

AI 도구들은 대화나 `tasks/current.md`가 지나치게 길어지면 컨텍스트를 잃거나 환각(Hallucination)을 일으킬 수 있습니다.
이때는 **컨텍스트 압축(Context Compression)** 을 실행합니다.

**압축 방법:**
1. `.ai/prompts/compress-context.md` 프롬프트를 사용하여 AI에게 현재 `current.md`의 요약을 지시합니다.
2. 완료된 작업의 핵심 인사이트는 `docs/decisions.md`나 `.ai/memory/patterns.md`로 옮깁니다.
3. 요약된 과거 작업 내역은 `tasks/archive/` 폴더 하위에 날짜별로 보관합니다.
4. `current.md`에는 아직 진행 중이거나 앞으로 집중할 핵심 작업만 가볍게 남깁니다.

## 마무리 (기능 완료 또는 하루 끝)

### 11. 작업 갱신

`tasks/current.md`를 업데이트한다.
완료된 항목을 체크하고 다음 작업을 명시한다.

```
## 완료 기준
- [x] 회원 생성 API 정상 동작   ← 완료
- [x] 중복 이메일 시 에러 반환  ← 완료
- [ ] 비밀번호 해싱 적용 확인   ← 아직

## 진행 상태
- [x] 회원가입 API (완료)
- [ ] 로그인 API (다음) ← 여기서 이어간다
```

> 다음 세션을 시작할 때 current.md만 보면 어디서 이어가야 하는지 바로 알 수 있어야 한다.

### 12. 컨텍스트 동기화

아래 파일들이 현재 상태와 맞는지 확인하고 틀리면 수정한다.
다음 세션의 AI가 읽을 "기억"이기 때문에 정확해야 한다.

| 파일 | 확인 내용 | 업데이트 예시 |
|---|---|---|
| `context.md` | 현재 단계, 완료된 기능 반영됐는가 | "현재 단계: 회원가입 완료, 로그인 진행 중"으로 수정 |
| `patterns.md` | 이번 작업에서 새로 발견한 패턴 있는가 | Controller-Service 패턴 추가 |
| `map.md` | src/ 구조가 바뀐 게 있는가 | controllers/, services/ 폴더 추가됐으면 반영 |

**확인 질문:**
```
- 내일 처음 프로젝트 여는 사람이 context.md만 봐도 현재 상태를 알 수 있는가?
- 새 팀원이 patterns.md만 봐도 코드 스타일을 파악할 수 있는가?
- map.md가 실제 src/ 구조와 일치하는가?
```

## 전체 흐름 요약

```
[시작]
컨텍스트 로드 → 작업 정의 (current.md 작성)

[반복]
AI 요청 (prompts 템플릿 사용)
  → 코드 검증 (요구사항 / 구조 / 추상화 3가지)
  → 수정 요청 (한 줄로 구체적으로)
  → 막히면 context.md / map.md 확인 후 재시도
  → 좋은 패턴 나오면 patterns.md 기록
  → 중요한 결정 생기면 decisions.md 즉시 기록

[마무리]
current.md 완료 항목 체크 + 다음 작업 명시
context.md / patterns.md / map.md 동기화
```

---

## 시간이 지나면

| 단계 | AI 상태 | 이유 |
|---|---|---|
| 초기 | 자주 틀림. 사람이 많이 수정. | patterns, decisions 아직 없음 |
| 중기 | 점점 맞춤화됨. 반복 작업 자동화. | 축적된 패턴으로 AI가 프로젝트를 이해하기 시작 |
| 후기 | 거의 팀원 수준으로 동작. | patterns + decisions 누적이 AI의 "경험"이 됨 |

> 이 구조의 힘은 patterns와 decisions의 누적에 있다.
> 매 작업마다 조금씩 쌓이는 것들이 AI를 점점 더 정확하게 만든다.
> 처음엔 느리게 느껴지지만 중기 이후부터 속도가 역전된다.
